# Social core phase 2 (isolated)
New PostgreSQL text posts (private by default, opt-in members-only), owner-only edits/removal, 5-second server-side posting guard, two-way block visibility, private likes and bookmarks. No anonymous feeds, media, counters, notifications, following, DMs or moderator access yet. App runtime is trusted server SQL only; GUC actor context is not authentication. Test on disposable PostgreSQL, not Neon production. Do not expose until moderation, account restrictions, private-account semantics, full API/driver auth and privacy review are done. Preserve old IDs only when backed by authorized exports; never link users based on matching handles/emails. Legacy migrations remain untouched.

## Authenticated social HTTP routes
The existing business transaction now provides own-profile text edits, bounded RLS-visible post pages, private-by-default creation, author-only post edits, independent like/bookmark toggles and request/accept/remove follow actions. A separate STARFLOW_SOCIAL_PREVIEW_ENABLED=true flag is required in the owner-guarded preview Worker in addition to existing v2 flags. No production or legacy routes changed. Tests use restricted PostgreSQL credentials and synthetic sessions; real Worker connection, UI integration, comments, moderation, deletion workflow, media and public visibility policy remain release gates.

## Post comments (022)
Additive text-only comments include author-only editing, parent-post visibility checks and two-way block filtering, bounded keyset pagination scoped to the parent, and a separate five-second per-author transactional throttle. Existing authenticated social preview routes expose these actions only behind the existing owner and feature gates. No public/production access or historical deletion. Parent deletion is deliberately restricted while comments exist; withdrawal/moderation lifecycle, threaded replies, comment notifications and original UI integration remain follow-ups. Integration tests exercise the restricted role with synthetic fixtures only.

## Comment replies and withdrawal (023)
One-level replies reference a visible non-withdrawn root comment in the same post, with a composite foreign key and an invoker trigger. No original content is quoted; list serialization suppresses references to invisible parents. A user's explicit withdrawal of their own visible new-system comment replaces its text with a tombstone and sets a server timestamp; rows and reply links remain, and the runtime cannot restore or edit withdrawn content. Legacy data is untouched. Repeating the action is idempotent when the comment remains visible. Withdrawal of a comment whose parent is no longer accessible, moderation, retention and actual frontend remain future work. Tests use isolated CI fixtures.
