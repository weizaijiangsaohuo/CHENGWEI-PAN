# Business API integration — isolated, not deployed
Five HTTP handlers for authenticated profile, DM incremental reads/sends and notifications reads/acknowledgements. Exact origin, bounded body and cursor, parameterized SQL, transaction-local role/actor, no cache, no public route. Tests use a disposable PostgreSQL service with a restricted role; fixture session adapter is mocked, real Better Auth integration and Neon/Workers validation remain mandatory. Staging inbox HTML/JS uses textContent, no local token storage, no background polling; it is not hooked to the production UI or a hosted preview. Admin queue still owner-only until real MFA issuer and restricted service role exist. No WebSocket transport provisioned. Need DM rate controls, retry idempotency, concurrent block/follow enforcement, paginated UI, real session tests, private media, UX/accessibility and deployment gates. Dependency recovery: upstream package tarball @better-auth/core 1.7.27 returned npm E404 before auth tests; pin core 1.7.26, rerun audit/install/tests. Retain old data and credentials until cutover. No external paid API or new cloud resources.
DM sends accept optional UUID requestId. The same authenticated sender can safely retry the same recipient/body/key: 201 on creation, 200 with the original ID on replay, 409 when reusing a key for a different visible payload. Keys are per sender; concurrent retries are arbitrated by the database unique constraint and only an actual insert triggers a notice. RLS still enforces blocked pairs. Legacy callers without requestId remain supported but are not retry-safe. Apply migration 013 in isolated staging only after CI, before enabling keyed requests. No existing records are removed or rewritten. Production client integration is pending.
