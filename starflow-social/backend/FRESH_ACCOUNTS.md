# New-account provisioning lab
Migration 024 implements atomic creation of a new ordinary profile/principal and explicit Better Auth UUID binding, using a dedicated NOLOGIN role that has no direct admission, auth, staff or profile table grants. An owner-only short-lived admission and a verified active session are both required; replay and handle collisions fail without reusing an older principal. No ordinary signup can choose its own authority, import a prior account, or receive a role. No admission issuer or public route exists. CI runs synthetic SQL fixtures in a rolled-back transaction and a server adapter unit test. Runtime attestation rejects the new gateway membership on both existing login roles. Migration 024 is installed only on the isolated Neon staging branch; keep production disabled until actual signup/verification/admission issue protocol, concurrent eligibility/revocation tests, free mail and secure credentials are ready. The user's legacy-account retirement request remains separate; no old data deleted by this work.

## Staging rehearsal and integrated acceptance

The transaction rolled back; the table and role were absent afterward and user/principal/staff counts remained zero. Do not broaden auth/business credentials or silently bypass the restricted-role test. The real-session CI now uses a separate disposable provisioning login, actual signup/email verification and guarded sign-in, synthetic owner-issued admission, ordinary-profile creation, replay and legacy privilege denial, then social/message/realtime-policy checks and logout. This does not implement live admission issuance or enable registration. A second rollback-only Neon rehearsal used a transaction-local owner membership for testing the actual restricted role; all 22 statements passed. The 8 migration statements were then applied to staging only, without that test membership. Counts of accounts, sessions, staff and admissions remain zero; existing login roles cannot execute or assume the new gateway. Live admission issuance is still not implemented.

## Registration admission issuer (migration 025)
Separate NOLOGIN issuer can execute only two narrowly scoped functions: issue once for a recent unverified credential account during a trusted new-signup callback, and check the exact unverified recipient against an active admission. It cannot provision accounts, edit staff, or directly read authentication tables. Existing auth/business runtime roles must never assume it. CI real-session test now uses the isolated issuer instead of direct owner insertion. This only tests the new-signup callback; it does not mount any public signup or resend endpoint. The 15-minute admission lifetime can expire after a failed email delivery; safe retry/restart and admission recovery policy remain unresolved. Migration 025 was applied on 2026-11-21 to isolated Neon staging only. Catalog checks confirmed the issuer can execute only its intended entry points, cannot provision or read auth/staff/admission tables, and both existing runtime roles are denied issuer execution. User, session, principal, staff and admission counts remained zero. No live mail, credentials or production change.

## Registration mail retry safeguard
The fresh-registration mail adapter rechecks the exact active admission after a committed mail budget and immediately before transport. If it expired, was consumed or became ineligible, it denies the send and retains the reserved attempt. Provider timeouts are not automatically retried or refunded. A later trusted verification callback uses a new event ID and the same recipient-based budget, with independent free billing verification. This does not enable a public resend route or extend expired admissions; live retry/restart remains gated.

## Integrated registration mail rehearsal
The disposable real-session CI now uses the actual fresh-registration mail callback, restricted admission issuer and a separate restricted mail budget login in the same signup/verification/provisioning flow. The provider account response and transport are synthetic; the committed recipient budget and fixed verification link are checked before the fixture records delivery. No live provider or public registration is enabled. Actual billing verification, secret provisioning, mail delivery and expired admission handling remain required.

## Request-scoped signup handler
The registration composition is now reusable server code rather than a test-only Better Auth override. It accepts only an explicitly enabled and owner-authorized preview signup and token verification, validates exact origin, limits input and disallows callback redirects, reset and resend routes. Each signup request creates its own auth instance and gates the trusted email callback on one issuance for its exact recipient. The integrated disposable CI exercises this handler with the restricted issuer and budget adapters. It is not mounted in the Worker; separate credentials, role attestation, live billing/transport, non-enumeration review, and recovery of incomplete signup remain release prerequisites. A valid email token alone does not create a business principal; the provisioning admission check is still required.

## Owner-gated Worker account initialization route
The existing preview dispatcher now supports POST /api/v2/account/initialize only with the independent STARFLOW_FRESH_PREVIEW_ENABLED=true flag (not configured), enabled preview and owner authorization. No input body or subject selector is accepted. It uses a separate sf_fresh_account_connect login with separately validated credentials and an attested single gateway membership, no direct table/column grants, and only the intended delegated definer function. The existing verified session and atomic admission consumption determine the new ordinary principal. Disposable real-session CI exercises the route, replay, malformed/unauthorized requests and temporary unsafe grants. No staging login created or activated, no production migration or legacy account deletion. Signup and its live mail provider still require separate activation.
